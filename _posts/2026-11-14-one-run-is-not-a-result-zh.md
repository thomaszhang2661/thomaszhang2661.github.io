[English version](/2026/11/14/one-run-is-not-a-result/)

我在 vLLM 里用 MATH-500 比较一种量化 KV cache 和 BF16。同一个模型、同样的 500 道题、贪心解码。第一次运行的结果是量化 cache 掉了 2.2 个点。

然后我把 BF16 又跑了两次，除了题目顺序什么都没改：

| 运行 | 正确率（BF16 KV） |
|---|---|
| 原顺序 | 66.6% |
| 打乱 1 | 65.0% |
| 打乱 2 | 63.8% |

DeepSeek-R1-Distill-Llama-8B，vLLM 0.33，H200，最多生成 4096 个 token。光是基线自己就差了 2.8 个点，任意两次运行之间约有 47 道题对错不同。每个配置跑三次取平均后，量化 cache 的差距从 −2.2 缩小到 −0.33 个点（配对置换检验 p = 0.83）。

这个模型属于波动大的：约 30% 的回答撞到 4096 token 的上限，被截断的思维链很容易往任一边倒。Qwen2.5-7B-Instruct 上，BF16 跑五次只在 71.0–71.6% 之间。但量化配置比 BF16 波动更大：同样在 Qwen2.5-7B-Instruct 上，一个量化配置在 200 道题上一次 67.0%、另一次 73.5%（批的组成和 GPU 节点不同）。

## 为什么同一个配置会得到不同的答案

**1. 贪心解码“本来应该”是确定的。** 贪心解码每一步都选概率最大的 token。同样的输入、同样的模型，按理说每次都该选出一模一样的 token。

**2. 计算机里的加法，换个顺序结果就可能不同。** 计算机存的数位数有限，每做一次加法都要舍入，所以先加哪个、后加哪个，结果可能不一样。假设只能保留 3 位有效数字：

- 先算 1000 + 4 = 1004，舍入成 1000；再加 4，还是 1000。
- 先算 4 + 4 = 8，再算 1000 + 8 = 1008，舍入成 1010。

同样是 1000、4、4 三个数相加，一个得 1000，一个得 1010。BF16 只有大约 2–3 位有效数字；GPU 算子内部累加一般用 FP32（约 7 位），差别小得多，但依然存在。

**3. 加法的顺序，取决于“这一批里有多少个请求”。** 推理服务会把很多请求放在一起成批计算。GPU 算子为了跑得快，会按批的大小选不同的算法：批小的时候，把一次很长的求和（矩阵乘法里沿隐藏维度，注意力里沿上下文）拆成几段并行算再合并；批大的时候换一种分块方式。拆法不同，加法的顺序就不同。所以同一个请求，和不同的请求放在一批里，算出来的数值会有极小的差别，比如概率在小数点后第四、五位不一样。“批不变”的意思是：不管和谁一起算，同一个请求的结果都完全一样。现在的大多数算子做不到这一点，Thinking Machines 指出这才是结果不确定的主要原因。

**4. 打乱题目顺序，“和谁一批”就变了。** 我只打乱了题目顺序，别的什么都没改。但 vLLM 是连续成批的：有请求算完，新的请求就补进来。顺序一变，每一步里同时在算哪些题、一批有多大，也就跟着变了。

**5. 极小的差别，怎么变成答错题。** 大部分时候，概率最大的 token 远远领先第二名，小数点后第五位的差别改变不了结果。但偶尔会遇到两个 token 的概率几乎一样（比如 0.4001 对 0.4000），这时那一点点差别就足以让选中的 token 翻转。每个 token 都依赖前面所有的 token，一个 token 不同，后面整段生成都会走上另一条路。推理模型一次要生成几千个 token，总有某一步碰上这种“几乎平局”，于是思维链分岔，最后的答案可能变对，也可能变错。

这就是同一个配置跑三次，正确率是 66.6%、65.0%、63.8% 的原因。

**前人的工作。** [Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)（Horace He，2025）：根本原因是算子不是批不变的；他们写了批不变的算子，让 vLLM 跑出了完全确定的结果，代价是慢一些。Yuan 等人（[arXiv 2506.09501](https://arxiv.org/abs/2506.09501)，初版题为 “Give Me FP32 or Give Me Death?”）：BF16 的有效位数太少，最容易出现这种翻转；改用 FP32 计算，差别小到几乎不会改变选择。他们测到，在 BF16 下只改批大小、GPU 数量和型号，R1-Distill-Qwen-7B 的正确率就能差到 9%。

## 对比较 KV cache 格式意味着什么

量化 KV cache 本身也会带来很小的数值差别，大小和这种运行之间的波动差不多，也会触发同样的分岔。所以只跑一次、看到差了两三个点，根本分不清是量化造成的，还是这次碰巧分岔了。

我现在的做法：

1. 每个配置至少跑三次，每次打乱题目顺序。
2. 用全部题目，不用子集。
3. 逐题配对比较，用符号翻转置换检验，而不是只看平均数。
4. 报告差距时，同时给出基线自己的运行间波动。

这件事也让我撤回过一个结论：根据 200 道题上的单次运行，我曾报告某个配置掉了 5 个点（p = 0.011）。换成 500 道题、跑五次后，差距变成 −1.9 个点（p = 0.17），我把它撤回了。
